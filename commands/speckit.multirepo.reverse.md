---
description: Reverse-engineer baseline specs from existing member repositories — exposed contracts, data model, behaviors, external dependencies, and implicit constitution rules — automatically or in a guided conversation, with file:line evidence for every statement
---

## User Input

```text
$ARGUMENTS
```

Accepted forms:

- `auto [<member-id>...]` — scan the listed members (default: every cloned member), propose one baseline spec per member, confirm, write.
- `guided [<member-id>]` — start from one member and build its baseline spec capability by capability in a conversation; the user supplies the business rules the code cannot show, and confirmed neighbours become the next stops.
- `contracts-only` — copy and normalize the interface specs found in every cloned member into the central repository. Deterministic: no inference, no conversation.
- empty — ask the user which mode to use (headless: behave as `auto`).

## Purpose

This repository is the **central specs repository** of a multi-repo workspace whose members already contain code but no specs (a brownfield workspace). This command reads that code and writes a **baseline** per member — what the member does *today* — so the first real feature starts from documented ground instead of from memory:

| Output | Path (central repository) | Written by |
|--------|---------------------------|------------|
| Interface specs, normalized | `specs/baseline/<member-id>/contracts/` | every mode |
| Baseline spec | `specs/baseline/<member-id>/spec.md` | `auto`, `guided` |
| Proposed type constitution | `constitutions/<type>.md` (or `constitutions/<type>.proposed.md`) | `auto`, `guided` |

A baseline directory is **not a feature**: it has no plan, no tasks, and is never dispatched. All baselines live under the single directory `specs/baseline/`, which has no numeric prefix whatever the member ids are, so Spec Kit's feature numbering (`specs/NNN-*`) ignores it; and baseline contracts sit at `specs/baseline/<member-id>/contracts/`, outside the `specs/<feature>/contracts/` pattern that feature tooling reads. Spec Kit's own commands do not look for baselines: to use one as "current behavior" while specifying or planning a feature, cite it in the prompt (e.g. `/speckit.specify … — current behavior: specs/baseline/orders/spec.md`). `/speckit.multirepo.tasks` reads the baselines of the members a feature touches when it splits the tasks.

It reuses the scan engine and the evidence model of `/speckit.multirepo.domain` — same places to look, same bounded-scan rules, same confidence levels — but its output is specs, not manifest fields.

Rules that apply in every mode:

- **Evidence or nothing.** Every statement in a baseline spec cites at least one `file:line` in the member repository (paths relative to the member root; prefix with `<member-id>:` when citing another member, or `.specify/memory/domain.md` when the statement comes from the domain map). A statement the user makes without evidence is recorded with `evidence: user` — never silently invented. Low-confidence findings become **open questions**, never statements.
- **Every statement carries a status**: `confirmed` (the user confirmed it in this run) or `unconfirmed` (inferred and not yet reviewed). **Headless runs mark everything `unconfirmed`**, including edges the domain map lists as confirmed — cite the map as evidence instead.
- **Observed is not intended.** The code shows what a member does, not what it must do. Inferred statements describe behavior (`Consumes queue orders-created`); only the user turns behavior into a requirement (`MUST`) — in `guided` mode, by classifying it `intentional`.
- **Write scope.** This command writes only under `specs/` (baseline directories) and `constitutions/` (proposals). It **never modifies `.specify/workspace.yml`** — not `constitution`, not `domain`, not `communicates_with`, not `depends_on` — and never writes inside member repositories. When a finding suggests a manifest change, print the YAML and point to the command that owns it (`/speckit.multirepo.domain`, `/speckit.multirepo.workspace`).
- **No silent overwrite.** An existing `spec.md` or constitution file is never replaced without showing the diff and getting confirmation (interactive); headless runs never overwrite a file that contains `confirmed` statements or that was not generated by this command (see Step 5).

## Step 1 — Load the workspace

Read `.specify/workspace.yml` from the repo root. If it is missing or invalid, **STOP** with: `No valid workspace manifest at .specify/workspace.yml. Run /speckit.multirepo.workspace first (central specs repository).`

For each member note `id`, `path` (relative to this repo root), `constitution`, `domain`, and `communicates_with`. Check which member paths exist on disk; members that are not cloned cannot be scanned — list them as *unscanned* in the report (suggest `specify workflow run multi-repo-bootstrap` when they have a `url`). Member ids given in `$ARGUMENTS` must be declared in the manifest; **STOP** on an unknown id with the list of known ids.

If `.specify/memory/domain.md` exists (written by `/speckit.multirepo.domain`), read it — it becomes spec context:

- **Communication rows** whose map status is `confirmed` are carried into the member's *External dependencies* (and, from the other side, *Interfaces → consumers*) with the map as evidence; rows from an `unconfirmed` map, or low-confidence rows, are context only — re-verify them in the scan before stating them.
- **Domain notes** and the *Domains* table give the business vocabulary: use it for the *Overview* draft in `auto` (quoted, attributed to the map) and to phrase the business questions in `guided`.
- **External systems** listed in the map are external dependencies, never members.

Also note existing `specs/baseline/*/` directories (a previous run — see Step 5), `specs/*/contracts/` of real features — excluding `specs/baseline/` — (first-class interface evidence), and existing files under `constitutions/`.

## Step 2 — Scan a member (shared by all modes)

Run the scan of `/speckit.multirepo.domain` Step 2 for member `M` — IaC and deployment descriptors, interface specs, configuration, source, docs as corroboration only — and keep its communication hits: they feed *External dependencies*. Then extend it with four more kinds of finding. Record **every** finding as `(kind, file:line, snippet, confidence)`.

**Exposed contracts** — what `M` offers to others:

- Interface spec files: `openapi.*`, `swagger.*`, `*.proto`, `*.graphql` / `*.graphqls` / `schema.gql`, `asyncapi.*`, JSON Schema files referenced by them, `pacts/` where `M` is the provider
- Route handlers: Express/Fastify/Koa routers (`app.get(`, `router.post(`), NestJS/Spring/ASP.NET controllers and attributes (`@Get(`, `@RequestMapping`, `[HttpPost]`), FastAPI/Flask/Django routes (`@app.get(`, `@router.post(`, `urlpatterns`), Go `http.HandleFunc` / chi / gin / echo, API Gateway and Lambda URL routes in IaC, gRPC service implementations, GraphQL resolvers
- Published events: topics/queues/buses `M` writes to, with the message shape when a schema, type, or serializer names it

**Data model** — what `M` stores:

- Migrations (`migrations/`, `db/migrate/`, `alembic/versions/`, Flyway `V*__*.sql`, Liquibase changelogs, Prisma `schema.prisma`, Knex/TypeORM/Sequelize migrations)
- ORM models and entities (SQLAlchemy/Django models, JPA `@Entity`, EF `DbContext`/`DbSet`, TypeORM `@Entity`, Mongoose schemas, GORM structs)
- Raw `*.sql` (DDL: `CREATE TABLE`, indexes, constraints)
- IaC table and store definitions (`aws_dynamodb_table`, `AWS::DynamoDB::Table`, RDS/Aurora, `aws_s3_bucket` used as storage, Glue catalog tables, Redis/ElastiCache)

Per entity: name, fields with types, keys, constraints, relations — taken from the most authoritative source (the latest migration wins over a model; say so when they disagree, as an open question).

**Behaviors** — what `M` does on its own:

- Queue/topic consumers: SQS/Kinesis/DynamoDB-stream event source mappings, SNS/EventBridge subscriptions and rules, Kafka/RabbitMQ/Pub/Sub consumers (`@KafkaListener`, `consumer.subscribe`, `@RabbitListener`), Lambda handlers wired to events
- Scheduled jobs: cron expressions, `schedule_expression`, EventBridge schedules, Kubernetes `CronJob`, `@Scheduled`, Celery beat, Hangfire/Quartz, GitHub Actions `schedule`
- State machines: Step Functions ASL, workflow engines (Temporal, Camunda), xstate/statecharts, status enums with explicit transition code (`status = 'SHIPPED'` guarded by a previous status)
- Notable rules visible in code: validations, idempotency keys, retries/DLQs, timeouts — as behavior, never as requirement

**Implicit constitution signals** — the conventions `M` follows without writing them down:

- Error handling: error middleware/filters, custom error hierarchies, Result/Either types, problem+json responses, retry/DLQ policy
- Auth: auth middleware/guards/decorators (`passport`, JWT verification, `[Authorize]`, `@PreAuthorize`, API Gateway authorizers, IAM policies on the member's own resources)
- Logging and observability: logger library, structured vs plain, correlation/request ids, metrics/tracing SDKs
- Naming conventions: file and directory casing, resource naming patterns in IaC (`<env>-<service>-<resource>`), route style, table/column casing
- Tooling as declared rules: linter/formatter configs (`.eslintrc*`, `ruff.toml`, `.editorconfig`, `tsconfig` `strict`), test framework and layout, CI checks

A signal becomes a candidate rule only when it is **consistent** in `M`: report its prevalence (`structured logger in 14/15 handlers`) and the counterexamples (`src/legacy/export.ts:9 uses console.log`). One occurrence is a finding, not a convention.

**Confidence** (same scale as the domain command): `high` — declared in a spec, migration, IaC, or a framework registration (the code cannot run otherwise); `medium` — read from source by pattern, unambiguous; `low` — name similarity, dead-looking code, or docs only. Low confidence goes to *Open questions*.

**Capabilities.** Group the findings of `M` by discovered capability — a cohesive slice of behavior named after what it does (`order placement`, `refunds`, `nightly reconciliation`): a route group or controller, a consumer and the tables it writes, a scheduled job and its state machine. Each capability lists its interfaces, entities, behaviors, and evidence. Name capabilities from the code's own vocabulary; mark the names *proposed*.

Keep scans bounded: skip `node_modules/`, `.git/`, `vendor/`, `dist/`, `build/`, `target/`, `.venv/`, generated code, and binaries; prefer `rg` (fallback `grep -rn`) with the patterns above over reading files whole; read a file whole only when it is an interface spec, a migration, or a model.

## Mode A — `auto`

1. Scan the selected members (Step 2) and run the `contracts-only` copy for them (Mode C, steps 2–3) so *Interfaces* can link to the copied files.
2. Draft `specs/baseline/<member-id>/spec.md` per member (format in Step 3). Every statement is `unconfirmed`; *Overview* is drafted from the README, service name, domain notes, and capabilities — and says so.
3. Draft the constitution proposals (Step 4).
4. Present the **proposal** — per member, the capability list with counts, the spec draft, open questions, and the constitution proposal (or its diff) — then the unscanned members.
5. **Interactive**: ask the user to confirm or correct per member (and per statement when they want to), answer open questions, and add what the scan missed (`evidence: user`). Confirmed statements become `confirmed`; rejected ones are dropped; unanswered ones stay `unconfirmed`. Then write (Step 5).
   **Headless**: write everything `unconfirmed` (Step 5), constitutions only as `.proposed.md`, and print the paths.

## Mode B — `guided`

A conversation that turns observed behavior into intent, one member and one capability at a time. Mirrors the domain command's guided mode.

1. **Initial piece.** If `<member-id>` was given, start there; otherwise ask: *"Which member do you want to document first?"* Then ask one open business question: *"In a few sentences, what does this member do for the business — who relies on it, and what would break if it stopped?"* The answer becomes the spec's *Overview* **verbatim** (`confirmed`, `evidence: user`).
2. **Scan the current member** (Step 2), copy its contracts (Mode C, steps 2–3), and present its findings **grouped by capability**: per capability, the interfaces, entities, and behaviors with evidence and confidence, plus its open questions.
3. **Ask per capability.**
   - *"What business rule does `<capability>` implement?"* — the answer is recorded as the capability's business rule (`evidence: user`), in the user's words.
   - For each behavior: *"Is this `intentional` (the business needs it — it becomes a requirement) or `incidental` (an implementation detail or accident)?"* `intentional` becomes a requirement `FR-NNN: <Member> MUST …` with the behavior's evidence; `incidental` goes to *Observed behavior — not contractual*. Behaviors the user does not classify stay in *Behaviors* as `unconfirmed`.
   - Confirm or correct the capability name, its entities, and its interfaces; ask what is missing (*"Does refunds also have a manual path the code doesn't show?"*).
4. **Advance the frontier.** Members `M` communicates with (scan hits and domain-map edges) that the user confirms join a queue; show it (*"Next: payments, notifications. Continue with payments, pick another, or stop here?"*). Systems that are **not** workspace members are recorded under *External dependencies → External systems* — never as members, never added to the queue (if one should be a member, point to `/speckit.multirepo.workspace`). Scanning a neighbour often confirms the previous member's edges from the other side — say so.
5. **Stop when the user says so or the queue is empty.** Write each visited member's spec as soon as its capabilities are done (Step 5), so stopping loses nothing. Members never reached are listed as *not documented*.

The user can switch to a full sweep at any point (*"do the rest automatically"*): finish with Mode A over the remaining members, keeping everything already confirmed. Headless runs never use this mode — they behave as `auto`.

## Mode C — `contracts-only`

Deterministic: copy what the members already declare, infer nothing, ask nothing.

1. For every cloned member (in `auto`/`guided`: the members being scanned), collect the **interface spec files** found in Step 2 (not route handlers, not inferred schemas). A file under a feature `specs/*/contracts/` in this repository (not `specs/baseline/`) is already central — skip it.
2. Copy each file — and every file it references through a relative `$ref` / `import` / `include`, transitively — to `specs/baseline/<member-id>/contracts/<path>`, where `<path>` is the source path relative to the member root (`api/v2/orders.proto` → `contracts/api/v2/orders.proto`). Mirroring the member's layout keeps every relative reference resolvable without editing it, and keeps same-named files apart (`v1/orders.proto`, `v2/orders.proto`). Normalization is limited to: UTF-8, LF line endings, one trailing newline. Never reformat, reorder, rename, or edit content — references included. A reference that cannot resolve inside the member (it points outside the member root, to a URL, or to a missing file) is left as is and listed in the index as *unresolved*.
3. Write `specs/baseline/<member-id>/contracts/INDEX.md`: one row per copied file — path, kind (`openapi` | `asyncapi` | `proto` | `graphql` | `jsonschema` | `pact`, or `referenced` for a file copied only because another one references it), source commit (`git -C <member-path> rev-parse --short HEAD`, or `uncommitted` when the file has local changes) — and a *Not copied* list of route handlers that have no interface spec (`file:line`, method, path), so the gap is visible, and the *unresolved* references. Re-runs replace copied files and the index in place; nothing else in the baseline directory is touched.
4. Report per member: files copied, references resolved, undocumented routes, unscanned members. Suggest `auto` or `guided` to describe the rest.

## Step 4 — Constitution proposals

From the implicit constitution signals, propose one **type constitution** per member type. The type is the basename of the member's manifest `constitution` path when it has one (`constitutions/lambda.md` → `lambda`); otherwise propose a type from the member's runtime and IaC (`lambda`, `glue`, `node-api`) and let the user rename it. Members of the same type are merged into one proposal: a rule enters only when it holds in **every** scanned member of that type; rules true for one member only are listed as candidates for that member's local constitution (`<member>/.specify/memory/constitution.md` — never written by this command).

Each rule is a short imperative line with its evidence and prevalence:

```markdown
- Handlers MUST log through `src/lib/logger.ts` (structured JSON with `requestId`) — 14/15 handlers; exception: src/legacy/export.ts:9 — unconfirmed
```

Writing rules:

- **The file does not exist**: interactive — show the full proposal; on confirmation write `constitutions/<type>.md` with the confirmed rules. Headless — write `constitutions/<type>.proposed.md` only: an unreviewed file at the path a manifest references would reach dispatched agents as governance.
- **The file exists**: **never overwrite it.** Show a diff (existing vs. proposed: rules already present, new rules, rules the code contradicts). Interactive, on confirmation — write `constitutions/<type>.proposed.md` for the team to merge (or apply the confirmed additions to `<type>.md` only if the user explicitly asks). Headless — write `<type>.proposed.md` with the diff summary at the top.
- **The manifest does not reference it**: do not edit `workspace.yml`; print the `constitution: constitutions/<type>.md` line to add per member.
- Never touch the workspace constitution (`.specify/memory/constitution.md`); suggest `/speckit.constitution` for rules shared by every type.

## Step 5 — Write

Create `specs/baseline/<member-id>/` as needed. For an existing `spec.md`:

- generated by this command (header comment present) and all `unconfirmed` → replace it;
- otherwise (contains `confirmed` statements, or hand-written) → interactive: show the diff, keep confirmed statements and the user's *Overview* unless the user replaces them, write after confirmation; headless: leave it untouched and write `spec.unconfirmed.md` next to it.

Never write outside `specs/baseline/<member-id>/` and `constitutions/`; never modify `.specify/workspace.yml` or member repositories.

## Step 6 — Report

- Per member: the paths written, statement counts (`confirmed` / `unconfirmed`), requirements and incidental behaviors (`guided`), open questions left, contracts copied and undocumented routes.
- Constitution proposals: paths written, existing files left untouched with their diff summary, and the manifest `constitution` lines to add.
- Unscanned / not documented members and why.
- Suggested manifest changes found during the scan (missing `communicates_with` edges, a member type without `constitution`), as YAML to apply by hand or via `/speckit.multirepo.domain` / `/speckit.multirepo.workspace` — **this command changed nothing in the manifest**.
- Headless: a prominent note that **everything is unconfirmed** and how to review it (`/speckit.multirepo.reverse guided <member-id>`).
- Next step: start the first feature with `/speckit.specify`, citing the relevant `specs/baseline/<member-id>/spec.md` in the prompt (Spec Kit does not load baselines on its own; `/speckit.multirepo.tasks` does, when splitting tasks), and run `/speckit.multirepo.domain` if the domain map is missing or older than the baselines.
